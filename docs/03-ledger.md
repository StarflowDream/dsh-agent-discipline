# 能力账本：给「一次通过率」记账

## 为什么记账

和 agent 长期协作，最容易自欺的一句话是"最近稳多了"。

感觉不可复现、不可比较、也无法定位。账本把感觉换成三个可数的东西：一次通过、返工轮数、失败原因。

账本的价值不是给自己打分，而是**决定下一步往哪投**：哪一类活一次过不了、卡在哪一种原因上。

## 口径

先把词定义死，否则数据没法比：

- **一次通过**：第一次跑判据就绿，中间没有返工。
- **返工轮数**：判据从红到绿之间，**修改**的次数。命令重试、读文件、加日志都不算。
- **诊断轮数**：定位原因花的轮数，单独记。它跟返工轮数不是一回事——一次改动可能花四轮才定位到。
- **挂起**：卡在需要外部输入（用户决定、环境缺失）的环节，不是"改不动"。要写清楚等什么。

## 记什么

| 字段 | 说明 |
|---|---|
| 日期 | 按天 |
| 任务 | 一句话，能对上判据 |
| 判据 | 跑哪个命令 |
| 结果 | 一次通过 / 返工 N 次后过 / 挂起 / 阻塞 |
| 返工轮数 | 数字 |
| 失败原因 | 写根因，不写现象（"按异常名判定，被运行时包装" 而不是 "报错了"） |
| 备注 | 值得下次再看的操作细节 |

**失败原因的写法决定账本有没有用**。"实现错 / 判据错 / 环境问题 / 需求没定"这几个类目比自由文本有用——它们直接指向不同的对策。

## 怎么读

几条规矩，都是从坑里爬出来的：

1. **样本少于十条，别看百分比**。3 单里过 2 单是 67%，5 单里过 3 单是 60%，这两个数的差别没有意义。
2. **挂起不算失败**。卡在用户决定上的任务不该算进通过率，否则数字会随外部条件漂移。
3. **分母写清楚**：是"已完成的单里过几单"，还是"全部单里过几单"。后者把挂起也压进分母，会系统性偏低。
4. **看分布不看均值**：同一个人做"改配置"能连过 5 单，做"排故障"可能 3 单返工 2 次。均值会把这条信息抹掉。
5. **失败原因比通过率重要**：通过率只说明"好不好"，原因分布说明"往哪修"。

## 样本要攒多少

先分项，再攒量。

按任务类型分：改代码、排故障、写文档、查资料、配置变更。每类跑 3 到 5 单才谈得上倾向。全混在一起攒 30 单，等于没有数据。

另一个真实结论：**样本是仪表盘，不是发动机**。攒样本本身不提升能力，它只保证你知道该修哪儿。所以它值得做，但不值得为它停下正在做的事——顺手记就行。

## 与判据的关系

账本的质量上限由判据决定：没有判据的活只能记成"人看了，说还行"，这既不可比也不可复算。

所以两者是一套：判据提供"过没过"的客观信号，账本提供"过不过得去"的分布。判据写得松，账本就会漂亮而没意义——这也是元判据存在的另一个理由。
