# 四层分工：行为层 / 技能 / 守卫插件 / 档位插件

把"让 agent 按规矩干活"这件事拆成四件独立的东西，各自有明确边界。混在一起会互相打架，也很难单独升级。

## 各层是什么

| 层 | 形态 | 生效方式 | 强制度 |
|---|---|---|---|
| 行为层 | 一段注入到会话开头的文本 | 每个请求都在上下文里 | 软约束（模型自觉遵守） |
| 技能 | 按需加载的流程文档 | 命中场景时才进上下文 | 软约束（按需、更细） |
| 守卫插件 | 代码拦截 | 工具调用前/后实时执行 | 硬拦截（做不到就是做不到） |
| 档位插件 | 按档位改适配器行为 | 与档位绑定 | 配置 + 部分硬拦截 |

## 各自该管什么

**行为层**：跨任务通用的态度与纪律。说话方式、确认边界、汇报规矩、验证要求。特点是短、普遍、每次都在。适合写"永远成立"的话；不适合写只在特定场景成立的步骤。

**技能**：一类任务的具体流程。装插件、发版本、排某类故障、写某种文档。特点是长、具体、按需加载。技能正文可以几百行，因为它只在需要时占上下文。

**守卫插件**：必须 100% 发生的动作。未读文件就改、危险命令、删库、把密钥写进仓库。行为层说"不要这样"是概率，插件拦截是确定性。凡是"绝不能发生"的，别指望条文，写成拦截。

**档位插件**：按任务难度给不同强度的资源。简单活别上深度思考（省时省额度），难活别硬撑低档（会反复返工）。它管资源配置，不管具体纪律。

## 一个需求该落到哪层

| 需求 | 落点 | 理由 |
|---|---|---|
| "回答先给结论，不要开场白" | 行为层 | 每轮都适用，短 |
| "发版前必须跑三关检查" | 技能 | 只在一类任务里适用，步骤多 |
| "改文件前必须先读过它" | 守卫插件 | 必须 100% 发生，软约束不够 |
| "难题自动用更高档位" | 档位插件（+ 行为层提醒） | 资源分配问题 |
| "子代理回报要先看产物再采信" | 行为层 | 判断纪律，适用于所有委派 |
| "不能把密钥提交上去" | 守卫插件 + 行为层 | 硬拦截为主，条文为辅 |

## 几条经验

**先软后硬，但别停在软。** 先用条文试，因为写得快、改得快；但同一个错犯第二次，就该升级成机制。条文治不好习惯性错误。

**层级之间不要重复。** 同一句话写在行为层和技能里，会让人误以为是两件事，改了其中一处就产生矛盾。定好归属，只写一处。

**硬拦截要给出路。** 拦截如果只有"禁止"没有"怎么办"，人就会去找绕过的方法（在插件外面执行、写脚本、拆成两步）。每条拦截都要有一条明确的替代路径。

**档位不是万能的。** 升档提升的是模型的判断力与持久力，补不了缺机制的问题（比如"必须拦截"这类需求，低档高档都不该发生，该由插件解决）。

## 与验证的关系

四层都在"让 agent 做对的事"，但**没有任何一层能证明它真的做对了**。

那是判据与账本的事：把四层的产出拿去看、去数。这也是本仓与行为层类插件的分工——一个负责约束，一个负责验证，谁也不替谁。
