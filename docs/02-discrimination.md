# 元判据：绿不算数，报红才算

## 一条判据的两种坏法

判据可以同时是绿的、又同时什么都没测。真实发生过两次：

**第一种：判定依据本身不成立。**

```js
// 打算：认出"是我们自己的计时器把请求掐了"
if (err?.name === 'AbortError') code = 'STALLED'
```

实际运行时把异常包装过一层，`err.name` 根本不是 `AbortError`，`message` 是 "The operation was aborted"。
于是这个分支从来没走进去过，判据测的是空气——它绿着，但它检查的那个东西从来没被触发。

正确写法是查状态而不是查名字：

```js
if (controller.signal.aborted) code = 'STALLED'
```

**第二种：要求了机制上做不到的事。**

某条判据要求"运行中的宿主把它内存里的状态表写回磁盘"。宿主不会这么干——它在启动时读一次，之后以内存为准。
于是这条判据永远红；为了让它绿，有人会去放宽断言，然后是另一种永远绿。

判据必须建立在**被测系统的真实契约**上。写之前先问：这个行为是它保证的吗？找不到保证，就不是契约，是期望。

## 元判据的做法

给每条判据配一个坏样本，跑一遍，**期望它报红**：

```
ok    agents-behavior-layer   坏样本如期报红  编号缺号：40；编号有重复：94 条覆盖 1..95
ok    ninfer-engine-ready     坏样本如期报红  缺 engine ready 行
FAIL  effort-override         坏样本没报红（这条判据测不出问题）
```

没报红的判据要当场处理：要么它判定条件太松，要么它根本没在读你指过去的样本。

坏样本的最低要求是可撤销：在工作目录里造副本、用环境变量把判据引过去，绝不改动真文件。判据要支持"指向别处"的口子（环境变量或命令行参数）——没有这个口子的判据没法自证。

## 两个真实踩过的坑

**坑一：坏样本位置对不上。**

给"改动覆盖"类判据造样本时，把内容写进了 `lib/effort-override.js`，而被测插件里真实存在的文件叫 `lib/overrides.js`。
凭空建的文件没有任何代码 import 它，判据照常绿——它根本没读到样本。

教训：造样本前先列出被测目录里的真实文件名，别按名字猜。

**坑二：坏样本没照判据语义造。**

给"委派模型配置"判据造样本时，把配置清空。判据内部把"留空"理解成"不接管模型"——也就是**正常状态**，于是它绿。

正确的坏样本是：填上一个判据明确断言不该出现的值。

教训：先读判据断言什么，再决定什么叫"坏"。"看起来坏"和"在判据眼里坏"不是一回事。

## 没有口子的判据怎么办

有些判据把路径、版本、常量写死在文件里，没法指向坏样本。两条路：

1. **给判据开个口子**（推荐）：把常量改成 `process.env.X ?? '<默认值>'`，默认行为不变，但可注入。这是低风险的机械改动，改完跑一次确认真环境仍然绿。
2. **承认它没被验证**：在元判据输出里单列"没有注入缝"的清单，明确写出它们从未被证明过。

清单 2 比假装覆盖完整有用。看的人一眼就知道哪些判据是可信的。

## 什么时候跑

- 新写一条判据：写完立刻配用例，跑一次。
- 改一条判据的断言：重跑它的用例（断言改了，坏样本可能不再坏）。
- 定期：元判据接进判据总闸（它自己也是一条 `*.check.mjs`），跟着主流程一起跑。
