# 判据：把「做完」变成可观察的信号

## 一条判据是什么

一个能跑的命令，加一个期望信号。命令退出 0 就是过，非 0 就是没过；三态之外还要能说"没法判定"。

判据要盯的是**可观察事实**，不是意图：

- 好判据：`vendor/pack.js` 与 `node_modules/dsh-x/pack.js` 逐字节一致。
- 坏判据：代码"看起来应该没问题"。

意图无法执行，事实可以。凡是写不出"跑什么命令、看什么信号"的验收标准，实际都还没定义完。

## 先写判据，再动手

顺序反过来会吃两次亏：先是不知道什么时候算完（于是反复返工），然后是做完之后补的判据往往照着实现写，实现错了判据跟着错（于是永远绿）。

动手前应该能回答：

1. 跑什么命令？
2. 期望什么信号（退出码 / 字段值 / 行数 / 差异为空）？
3. 现在跑它是什么结果？（应该是红的，否则说明这件事已经做完了）

第 3 问是关键：**判据要先跑一次看它红**。一次就绿的判据可能是"这件事本来就没坏"，也可能是"这条判据什么都没测"——不先看一次红，你分不清这两者。

## hard 与 weak

- `kind: 'hard'`：挡住交付。红了就不许说完成。
- `kind: 'weak'`：只提示，不挡门。适合风格类、建议类、需要人判断的项。

分档的意义在于让"红"保持可信：如果所有项都是 hard，人很快学会忽略红；如果所有项都是 weak，判据就成了装饰。原则是——**能挡门的一律 hard，挡不了门的别假装 hard**。

## 无法判定（退出码 2）

有些判据在特定环境下无法执行：缺依赖、缺凭证、目标不存在。这类情况应该报"无法判定"，而不是"失败"，也不是"通过"。

- 报失败会训练人忽略失败（因为红得没有道理）。
- 报通过更糟：一件没验证的事被记成已验证。

运行器把退出码 2 记成 `SKIP`，不计入失败，但也不计入通过，单独显示。

## 双形态：为什么运行器要防一件事

历史上有些判据是独立脚本形态的——顶层就 `process.exit(...)`。

绝对不能对这类文件用 `import`：import 会执行它的顶层代码，它一 exit 就把整个总闸顶掉。后果是几十项一项没跑、退出码还是 0，看起来"全绿"。

所以运行器的规则是：源码里有 `export default` 的走 import 快路径，没有的丢进子进程按退出码判定。

## 判据不该写死的东西

这几类判据会随时间腐烂，写的时候绕开：

- **写死版本号**：`pkg.version !== '1.0.0'` 会在下次升版时变成假红。要写就写格式（三段 semver）与自洽关系（与 CHANGELOG 首条一致）。
- **写死条数**：`assert(rows.length === 78)` 会在正常增删时变成维护负担。要写就写区间、或者"与另一个来源相等"。
- **写死时间**：除非判据本身测的就是时效，否则任何 `new Date()` 的比较都会在某天开始随机红。
- **写死绝对路径**：本机路径在别人机器上必然不存在。路径应该来自环境变量，默认值才是本机路径。

## 判据的覆盖面是有限的

判据擅长：配置、通道、文件一致性、接口形状、账本、产物清单、格式。

判据不擅长、也不该假装能测：输出质量、分析是否准确、方案是否合理、有没有考虑周全。

这一块必须人看。承认这条边界比给质量编一个分数更有用——一个假的分数比空缺危险得多。
